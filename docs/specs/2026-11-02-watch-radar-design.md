# watch-radar — design note (2 Nov 2026)

## Intent
The owner wants continuous, unattended research on sales of a few specific watch references: new listings worth looking at, how asking prices are moving, and auction lots coming up. The result should land in the inbox without the owner's Mac being on.

## Decisions (owner approved the chat description on 2 Nov 2026 with "go with your assumptions"; items marked *my call* are Claude's)
- **Runner:** Claude Code scheduled cloud routine, daily 07:00 Australia/Brisbane = `0 21 * * *` UTC. Monday (Brisbane) runs add a weekly price roundup. *My call:* one routine rather than two, so there is one thing to pause.
- **Memory:** this GitHub repo. The routine commits state and a per-run report to `main`. Cloud sessions start empty, so without this every run would repeat itself.
- **Delivery (changed 3 Nov 2026):** no email. A static web app (`index.html`) on GitHub Pages reads the committed `data/` files; the routine's last step is writing `data/latest.json` and pushing. The page shows a fresh/stale/failed status from `run_date`, so a silent failure is still visible. History: owner first ruled out the work Microsoft account (M365 connector detached 2 Nov), Resend to Hotmail was built, then superseded by the web app on 3 Nov.
- **Below-market (added 3 Nov 2026, owner's request):** per watch, a median asking-price benchmark across all readable markets (like-for-like on condition, 30-day median), listings under it ranked by discount and flagged verify / grey-new / clean. *My call:* median not mean; 3% threshold; 25%+ under is auto-flagged verify. Grey-market new sellers added to the source list because that is where below-market new pieces live for non-allocation brands.
- **Watchlist shape:** reference-level entries with condition list, full-set flag, AUD ceiling, markets and an `active` flag, in `data/watchlist.json` (moved from YAML on 3 Nov so the site can read and write it).
- **Owner control from the site (3 Nov 2026, owner's request):** a Watchlist tab with brand-level focus toggles, per-reference pause/edit/remove and an add form. Saves go through the GitHub Contents API with a fine-grained PAT held in the browser's localStorage. *My call:* PAT over any backend, because the site is static and the owner is the only writer. Paused entries are skipped by the routine but stay on the site.
- **Visual redesign (3 Nov 2026, owner's request, second pass):** after NOMOS Glashütte's site, measured live: white, Gotham Light 300 at ~16.6px body / 43px light headline, #111 text, #6e6e6e secondary, #e2e2e2 hairlines, #f7f7f7 panels, centred letterspaced wordmark, text-link navigation, hairline outline buttons, very large margins. Gotham is proprietary, so Montserrat 300/400/500 from Google Fonts stands in. One red (#d7282f) reserved for the pending dot and "verify". Dark mode kept as an inversion. An earlier brutalist pass the same day (paper/ink, heavy rules, mono) was superseded at the owner's request. Chart series colours unchanged (validated palette).
- **Third pass, 3 Nov 2026 (owner: "more minimalistic, re-look at the hierarchy, include images"):** tabs removed; one continuous page with a sticky hairline anchor bar (Today · Watches · Auctions · Runs · Watchlist). *Today* leads with the ranked under-market list across all watches, each row with a round thumbnail. Each watch is one section: photo (4:5, sticky) beside figures, chart, table, its matching listings and its auction lots; New listings / Price drops / Price history as separate views are gone. Photos: Wikimedia Commons, CC/PD only, cropped square, credited in-image and in the footer, stored in `images/` with `data/images.json`; Tudor has none because the only Commons file is a snapshot of a printed catalogue page. Owner can override with an image URL per entry; routine fills gaps (ROUTINE_PROMPT §1E).
- **Sources:** Chrono24, WatchRecon, eBay, named dealers for listings; WatchCharts and eBay sold for price; Phillips, Sotheby's, Christie's, Bonhams, Antiquorum, Everywatch, Leonard Joel, Lawsons for auctions.
- **Model:** `claude-opus-5-5` since 3 Nov 2026 (owner approved after two Sonnet runs under-researched: 8 and 37 fetches, effort floor unmet). Started on `claude-sonnet-5-5`.
- **Privacy:** repo must be **public** for GitHub Pages on a free account (decided 3 Nov; owner said they don't mind). Watchlist and reports are therefore visible.
- **Initial watchlist:** four example references chosen by Claude so the first runs are real. The email nags until they are replaced.

## Non-goals
- Not a sniping tool. Daily cadence; the minimum a routine allows is hourly anyway.
- No bidding, offers, seller contact, account creation or block evasion.
- No price prediction. Numbers and dates only.

## Open items / to verify from the cloud
1. The routine can push to a private repo on `main`.
2. GitHub Pages is enabled on `main` and redeploys after the routine's push.
3. Chrono24 / eBay / WatchCharts pages are readable through WebFetch at least some of the time.
All three are checked by a manual first run at setup.

## Brand focus (added 3 Nov 2026, owner's request)
The owner wants to steer research by **brand** rather than by reference: 22 named brands (anOrdain, Christopher Ward, Doxa, Frederique Constant, Hamilton, IWC, King Seiko, Longines, MeisterSinger, Mido, NOMOS Glashütte, Omega, Orient, Oris, Paulin, Seiko, Sinn, Studio Underd0g, Tissot, Tudor, Unimatic, Zenith) and four AUD bands (300–1,000, 1,000–2,000, 2,000–2,500, 2,500–4,000). Selections live in `data/focus.json`, saved from the site's Focus section with the same PAT mechanism. The routine researches each selected brand inside the selected bands, groups listings into models, carries up to five models per brand (continuity preferred), benchmarks each model on the whole market, and reports deals only inside the bands. The reference watchlist stays as an optional extra. *My calls:* 5 models per brand; benchmark on all listings but deals only in-band; the four Claude example references were removed so the first brand run starts clean. Expected run length grows with the number of brands (roughly 10–20 fetches per brand).

## Password-protected saving (3 Nov 2026, owner asked for a password instead of a GitHub token)
Settings move out of GitHub: `watch_radar_settings` (public read) and `watch_radar_secrets` (no access) in Supabase, with security-definer RPCs `watch_radar_save(password, id, data)`, `watch_radar_check`, `watch_radar_set_password`; bcrypt via pgcrypto, 0.4 s delay on a wrong password. The site reads the table on load (falls back to repo JSON), saves via RPC after a password prompt (optionally remembered in localStorage), and offers Change password. The routine reads the table at step 0.2 and mirrors it into the repo. `data/backend.json` carries the public URL and anon key; when empty the token path remains. *My call:* RPC-in-Postgres rather than an edge function, so there is nothing to deploy beyond one SQL file.
